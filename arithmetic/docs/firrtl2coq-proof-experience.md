# 使用 firrtl2coq 证明香山算术电路的经验

本文记录 64 位 `Radix2Divider` 和 8 位 `ArrayMulDataModule8` 的实际证明经历，说明哪些工作属于电路证明，哪些属于解释器修复，以及下次应怎样组织。对应工具修复为 `2824907`，基于上游 csj 的 `ced58a8`。统计与结论按下文区分初次证明、目录整理和 Lemma 拆分后的验证，不代表 firrtl2coq 对任意 FIRRTL 电路的保证。

## 1. 最终证明了什么

- 除法器：生成器给出的 11 个原始 assert 目标全部完成，最终入口为 [Radix2Divider.v](../verification/firrtl2coq/Generated/Radix2Divider/Radix2Divider.v)，外部证明在 [Divider/Proof.v](../verification/firrtl2coq/Divider/Proof.v)。
- 小乘法器：5 个原始目标全部完成，包括三个压缩器模块类型在各实例上的断言和两个顶层断言，最终入口为 [ArrayMulDataModule8.v](../verification/firrtl2coq/Generated/ArrayMulDataModule8/ArrayMulDataModule8.v)，外部证明在 [SmallMultiplier/Proof.v](../verification/firrtl2coq/SmallMultiplier/Proof.v)。目标数不是实例数。
- 两者都从任意符号寄存器初值出发，经真实 reset 高电平一拍，证明随后任意有限步合法执行上的性质；不是只验证若干测试输入或有限展开周期。
- 最终命题精确使用生成器的 observation 和 legal-trace 定义。外部输入必须是类型、位宽匹配的确定比特向量，执行须成功，并满足源程序显式 assume。没有加入待证明 assert 作为前提。
- 历史验证：目录整理前，两者完整证明均通过 Coq 编译和独立 `coqchk`；按电路名整理目录后，两者再次通过编译，除法器也再次通过独立检查。
- 当前验证：将模型及性质定义与 Lemma 拆成两个文件后，除法器的 11 个和小乘法器的 5 个原始 `generated_assert_i` Lemma 均通过 `coqc`，每个通过一行 `exact` 引用外部证明。本轮两个目标都使用 `--compile-only`，未重复 `coqchk`。公理依赖仍只有上游 `ftype_eqn_eq`、`ffield_eqn_eq`，没有新增公理或 `Admitted`。

必须区分“在成功执行上证明安全性质”和“证明解释器对所有输入均执行成功”。当前最终目标包含执行成功前提，前者不能直接冒充后者。`coqchk` 检查证明项，也不证明转换器与真实硬件之间的完整语义一致性。

## 2. 先审查语义，再投入大规模证明

这次不能直接证明的地方，有些来自工具行为，有些来自证明组织。应先用最小电路判别原因，而不是不断扩大自动化策略。

| 遇到的问题 | 诊断与处理 | 经验 |
| --- | --- | --- |
| 不同模块 assert 标签相同 | 生成全局 Coq 定义发生重名；加入模块编号和出现序号 | 先验证生成文件可编译且性质没有丢失 |
| 寄存器与组合节点对应不同采样时刻 | 边沿后寄存器值与此前节点缓存可能混用；增加不提交寄存器的组合 observation | 对时序性质先画清读状态、组合计算、写状态的顺序 |
| Low FIRRTL 的复位在下一状态 mux 中 | 声明中的结构化初始化不足以模拟真实复位；任意初值后执行 reset 高一拍 | 不要把“初始化寄存器”与“执行复位边沿”混为一谈 |
| 长组合链不能充分求值 | 原预算漏计 node、invalid 和重复实例；按实际实例及接口同步补足计数 | 单模块测试不足以覆盖同一模块多个实例串联 |
| UInt 减法结果不对 | UInt 操作数误用有符号解释；改为无符号解释后按结果位宽截断 | 优先测试最高位为 1、混合位宽、负差值等边界 |

例如 4 位 UInt 的 `8 - 1` 应得到 5 位结果 7，不能将输入 8 解释成 -8。除法器实际用到混合位宽减法，因此这一错误会直接影响控制路径。

上述修改保留了分层 AST、位向量和周期解释器框架，但改变了部分执行语义、初始化策略及生成命题的前提。因此不能声称“模型完全没变”。工具变更说明见 [Formal initialization and observation](../../tool/firrtl2coq/Formal-initialization-and-observation.md)。

### 观察编号和输入域

旧接口把 0 当作尚未组合求值的结构化初始化状态，assume 只检查 1..k，而 assert 目标却允许 k=0。最终采用的新约定是：输入 0 用于真实复位边沿，普通边沿和边沿前观察依次使用后续输入；观察 0 是复位后的第一次有效观察。assert 和 assume 都按观察 0..k 检查。不能把这个变化描述成单纯给旧状态 0 补一个 assume。

`hvalue` 同时容纳比特向量和 `Needtobedefined` 等解释器标记。任意 8 位数与“尚未算出值”不是一回事：前者仍是合法比特向量，后者可能导致求值失败。新增限制只针对外部输入；内部组合求值过程仍允许未定中间状态。任意寄存器初值和内部 invalid 的符号选择继续保留。

复位识别只针对名为 `reset` 的指定类型顶层输入，强制高电平一拍。自定义名字、低有效复位等不能自动套用这一解释；无该端口时保留旧初始化入口。这是接口约定，不是通用复位识别。

## 3. 两个电路采用的证明路线

### 除法器：复用数学不变量，但先证明对应关系

已有 Lean／Rocq 路线中的数学证明提供了有用思路，但不能直接用于新的解释器模型。最终路线是：

1. 从原始 AST 提取节点表达式、寄存器和位宽，建立稳定组合值的描述。
2. 证明原解释器的节点求值、组合迭代、寄存器提交与这些描述对应。
3. 把解释器状态投影到已有数学状态，证明初始化和每一步的对应关系。
4. 复用已有数学不变量，再将结果传回原始生成 assert。

关键是“对应关系本身也要证明”。如果只假设两个状态转移函数等价，最后得到的是带额外假设的结果，不能算完成原电路证明。

### 小乘法器：组合权重守恒与时序不变量分开

小乘法器保留分层结构，需要同时处理压缩器实例、端口连接和流水寄存器。最终证明分为：

1. 证明压缩器的局部位运算性质，再连接到每个真实实例的环境。
2. 对 2,262 个稳定信号值建立依赖、位宽和求值对应关系，证明原来的 2,256 次组合迭代达到所需值。
3. 证明原周期解释器提交全部 56 个寄存器，其中 52 个是部分积列寄存器。
4. 将 52 个捕获位的加权和重构为部分积行，连接到有符号乘积模 65536 的结果。
5. 为 valid、expected、previous、holding 建立流水线不变量，分别证明 reset 建立及普通边沿保持。
6. 用不变量和 observation 对应关系关闭原始五个目标。

这比在总定理里展开整个解释器更容易定位错误。整数表达式用于组织代数关系，必须通过已证明引理连接到原位向量计算，不能自行替换电路状态转移。

### 具体证明技巧：让每一步只处理一种困难

**先从 assert 反推不变量。** 不必直接证明整个算术算法的所有性质。先看断言的使能条件、比较对象及跨周期关系，再补足能由 reset 建立、由一步转移保持的状态关系。例如乘法器顶层需要的核心关系是：valid 时列寄存器的加权和等于 expected；holding 时同一个和等于 previous。只写断言本身通常不够归纳，加入保存值与内部数据的关系后，才能把前一拍信息传到下一拍。除法器则按控制阶段组织不变量，让每个阶段只承担该阶段需要的范围、计数和数据关系。

**使用两层归纳，避免同时展开时间和组合逻辑。** 内层按组合依赖的层级证明值已就绪，配合迭代次数得到观察状态；外层对周期数归纳，证明 reset 后不变量保持。先完成“单次观察正确”和“单步状态更新正确”，最后的任意步定理只调用这些引理。组合依赖的归纳参数与周期归纳参数应明确区分。

**对部分函数先提取成功结果，再做领域证明。** 解释器大量使用 `option`。把 `Some` 结果中的环境、类型和值通过小引理取出来，随后在明确的对象上推理。比如先由 `circuit_lookup path id states = Some value` 提取对应实例环境，再应用局部断言引理。这样可避免对巨大生成目标直接 `destruct` 时触发无关定义的展开。这个技巧只是在已有成功前提下整理目标，不构成执行总性的证明。

**对应关系要拆成可组合的小块。** 除法器复用旧数学模型时，先建立叶子输入和寄存器投影，再处理表达式、控制分支、下一状态，最后组合为一步模拟。不要一开始就证明两个完整 `step` 的大等式。保留适合具体问题的关系也很重要：原始解释器环境和抽象状态结构不同，通常应证明投影关系，而不是要求环境逐项完全相等。

**把位宽证明与数值证明分开。** 先证明字长和类型，再化简 `take`、零扩展及适配操作，最后进入整数或模运算。否则每一步代数推理都夹带截断条件。例如当 `size word = width` 时，先用独立引理消掉 `zext_to width (take width word)`。同理，必须先区分无符号解释与有符号解释，再讨论减法和乘法；范围证明可以把模等式提升为普通等式，但不能直接删去模运算。

**在计算边界选好表示。** 一位控制使用布尔值；多位数据保留位向量；加权和及乘积关系使用整数。三者之间通过明确的转换引理连接。一个布尔控制可分两种情况，一个小压缩器可穷举，但不要把整个时序状态空间也交给穷举。只有有限的局部真值表或输入域适合这种策略。

**分支沿真实控制逻辑展开。** 对 reset、enable、valid 等控制逐层分类，用对应控制引理立即消去不可达情况或确定下一寄存器值。对禁止更新的分支优先证明保持，对捕获分支优先证明新数据关系，再汇总为不变量保持。这样比对整个环境或所有寄存器同时分类更稳定。

**把映射操作封装为读写规律。** 环境中 `VM.add`、`VM.find` 和实例映射的嵌套很深。复用同键读取、异键保持和实例同步引理，明确哪些写入会影响目标。不要每次都从映射实现展开。对原解释器的连接和寄存器提交，尤其需要把读环境与写环境分开，避免把将要写入的值当成当前读出的值。

**让大定理只做组合。** 最终的五个或十一个目标应由已经证明的观察对应、局部 assert 和不变量推出来，而不是重新计算电路。使用显式 `conj` 组合固定数量的目标；用小的查找或存在性引理解包环境；只对当前节点暂时打开定义。若 `Qed` 明显比策略执行慢，优先检查是否在证明项中留下了巨大的隐式转换，而不是继续增加策略搜索。

**证明失败时先定位层次。** 用小实例或具体值区分：原语求值是否正确、节点是否已经收敛、端口是否同步、寄存器提交是否正确、数学不变量是否足够。对于实际发现的错误，保留最小回归；对于证明组织不合适的情况，调整引理边界。不要用增加输入限制或假设目标成立来绕过失败。

这些技巧不能取代对最终命题的审核。尤其是条件断言，应同时检查使能表达式的求值是否符合预期；只证明“使能成立则性质成立”，不足以说明使能计算本身没有错误。

## 4. 自动生成重复证明，可信边界留在 Coq

逐节点求值、位宽、端口同步和寄存器更新有大量同形证明。Python 适合根据电路结构生成这些定义和证明脚本；Coq 负责检查其输出。

生成器本身不是正确性的依据：脚本生成错误时，理想结果是证明无法通过。仍需审核最终命题与输入是否正确，因为生成器也可能生成错误或过弱的命题，而 Coq 只检查实际给出的命题。

当前已按真实 FIRRTL circuit/top 名称分离工具模型与证明，两个电路的 AST、性质和生成记录各自同目录：

| 电路 | firrtl2coq 生成目录 | 证明目录 |
| --- | --- | --- |
| `Radix2Divider` | `arithmetic/verification/firrtl2coq/Generated/Radix2Divider/` | `arithmetic/verification/firrtl2coq/Divider/` |
| `ArrayMulDataModule8` | `arithmetic/verification/firrtl2coq/Generated/ArrayMulDataModule8/` | `arithmetic/verification/firrtl2coq/SmallMultiplier/` |

每个生成目录包含 `Model.v`（逐字保留的模型和性质定义）、与电路同名的 `.v`（原始 Lemma 声明和一行外部证明调用），以及 `manifest.json`。复杂证明单独依赖模型，最终 Lemma 同时依赖模型和外部证明。
Coq 名称对应 `Divider.Model` / `Divider.Radix2Divider` 和
`SmallMultiplier.Model` / `SmallMultiplier.ArrayMulDataModule8`，不再使用旧 `ArithmeticFIRRTL` 命名空间。
每个电路的 `Model.v` 和电路同名 Lemma 文件都提交到 Git，供审核原始命题及一行证明调用；只有 `manifest.json` 保持可重建、忽略。此次调整仅修改后处理和证明引用，没有修改 firrtl2coq 本身。
手写证明和 Python 生成的证明证书仍放在同一证明目录，没有进一步拆分人工前后缀。

本次保留了较多阶段性脚本。下一次宜从开始就提供统一入口、输入输出清单和文件来源标记，并把“完全生成”与“保留人工前缀／后缀”明确区分。不要在生成文件中临时修改后忘记回写生成器。本次来源核对确实发现部分输出有人工补充，不能把所有文件都称为可直接重生成。

不再进入最终依赖的局部方案不表示结论错误。有些用于探索，有些被全局对应关系替代。按用户要求，它们保存在 [Archive](../verification/firrtl2coq/Archive/README.md)，保留原文、原路径和哈希，不参与最终构建。`CaptureAST.v` 虽不被最终 Coq 定理引用，仍被三个生成脚本读取，因此留在活动目录。

## 5. 大证明的性能经验

- 不要在最终总目标中直接展开巨大的实例表和解释器定义。先证明通用查找引理，再用它提取需要的环境。
- 大型生成命题上的 `repeat split` 可能继续展开内部量词和定义。用显式的有限层 `conj` 组合已经完成的目标更可控。
- 将“运行得到不变量”和“观察得到信号值”拆成独立引理。单块 `GeneratedObservation` 曾在 Qed 转换检查上耗时很长，拆分后显著改善。
- 对巨大的稳定值定义有选择地使用 `Opaque`，只在证明对应节点时展开；避免无意触发整张电路的转换计算。
- 有限枚举适合小压缩器和 8 位输入关系，但编译速度与独立内核复核速度不同。前端 65,536 种输入组合的检查会明显增加 `coqchk` 时间。
- `coqchk -silent` 长时间没有输出不等于卡死。检查进程状态、CPU 时间和日志后再决定是否干预；不要反复重启完整检查。

目录整理前的一次验证中，小乘法器的 140 文件强制重编译约 43 分钟，随后独立检查约 32 分钟。这是当时环境的一次运行观察，不能作为跨机器性能基准。

### 超长证明对象：优先减少展开和重复，再调整构建方式

这里需要区分三种规模：生成的 `.v` 文本、编译后的 `.vo` 证明项，以及检查时临时展开产生的计算量。它们并不成正比：几行 `vm_compute; reflexivity` 也可能要求内核复核很大的计算，而大量重复文本可能包含结构简单的证明。因此不能只根据代码行数选择优化。

本次已经验证有效的是拆分引理、控制透明性、避免总目标上的自动展开，以及按依赖增量构建。下面的结构性优化尚未在这两个电路上完成，属于后续方向，不应算作现有结果。

| 方法 | 主要解决的问题 | 应注意的限制 |
| --- | --- | --- |
| 通用引理加电路实例化 | 为每个节点重复输出同一种求值、位宽或连接证明 | 通用结论必须覆盖原始解释器的真实行为，不能假设电路正确 |
| 可证明的证书检查器 | 把大量逐节点证明换成紧凑数据和一次统一正确性论证 | 检查器及其可靠性定理需要在 Coq 中证明，外部脚本只能提供不可信证书 |
| 保留共享的表达式 DAG | 避免同一子表达式被反复展开成树 | 共享定义若在转换检查中反复展开，仍会有开销；需配合抽象引理 |
| 以模块契约组合实例 | 避免重复证明相同压缩器的全部内部计算 | 必须证明实例端口、状态更新和契约的连接关系，不能跳过分层同步 |
| 代数分解代替大规模枚举 | 减少对所有输入重复解释整张电路的计算 | 仍需证明代数表达式与实际位向量 AST 对应 |
| 分层引理、适度分文件 | 控制单次转换检查、内存峰值和失败重编译范围 | 分文件本身不会消除重复证明，也不保证总 `.vo` 更小 |

**最值得优先尝试的是通用引理和证书检查器。** 例如把每个节点的表达式、位宽、前驱编号和拓扑层级编码为数据，由 Coq 函数检查：每条依赖有效、类型吻合、层级严格递增、每种语句的局部规则满足。先证明“检查返回 true，则原解释器经过给定迭代后满足所需对应关系”的通用定理，再对具体电路提供证书。Python 生成证书即可，无需为每个节点拼出长段策略文本。检查器返回 true 的结论仍必须通过 Coq 接受的证明得到，不能只读取 Python 的成功标志。

本项目已有 `NodeCertificateCheck.v` 等局部检查与证书思路，但尚未把全局节点、端口、提交和收敛证明统一成这种形式。把现有生成证明进一步数据化，是减少代码规模的候选方向，而不是已经实现的优化。

证书检查器也不是自动消除所有成本：大证书的求值仍要复核。可按子模块或拓扑层分块，分别证明检查结果，再通过通用组合引理汇总。这样能复用已检查块，并定位失败位置。分块边界应携带紧凑的接口事实，避免把整个状态环境或全部中间等式复制进每个结论。

**对乘法器的有限枚举，可优先尝试结构化算术证明。** 单个小压缩器的真值表很小，保留枚举通常合适；对两个 8 位输入的 65,536 种组合，则可以尝试按 Booth 编码、部分积和权重守恒分解，用通用位运算／整数引理连接。这样有望减少重复运行解释器的工作，但是否更快、更小必须实测，不能单凭证明脚本更短判断。

**缓存和信任边界要明确。** 保留输入、生成器、工具、依赖的哈希，可以安全判断哪些构建结果需要更新；仅凭文件时间戳不够。独立 `coqchk` 通过后，未改变的源码不必每次全量重查；应明确记录哪个版本完成了覆盖全部依赖的独立检查，不能把编译通过与独立检查通过混写。跳过依赖检查、引入公理、留下 `Admitted`，或直接信任外部求解器的布尔结果，都不能作为本项目缩短证明的办法。

建议下一轮先对 `GlobalNodeSteps`／`GlobalSyncSteps` 中一种重复规则做小规模试验，同时测量 `.v`／`.vo` 字节数、`coqc` 时间、`coqchk` 时间和峰值内存。只有确认完整检查成本下降，再推广到全电路。检查器路线可能降低文本规模却提高求值成本，需要用同一工具链、同一命题和相同依赖检查范围比较。

## 6. 完成标准和复现

生成成功、语法通过、最终定理编译成功、独立检查通过是不同阶段。生成器自带的 `Admitted` 是待证模板，不能导入它来宣布证明完成。后处理逐字保留目标的 Lemma 声明，只将 `Admitted` 换成对外部定理的 `exact` 调用；最终必须编译这些 Lemma，不能只编译命题定义。

使用当前工具版本时，从仓库根目录执行：

```sh
# 工具语义修改后：先重编 Coq 和提取，再构建 OCaml。
(cd tool/firrtl2coq && opam exec --switch=firrtl2coq -- coq_makefile -f _CoqProject -o Makefile && opam exec --switch=firrtl2coq -- make -j1)
(cd tool/firrtl2coq/src/ocaml && opam exec --switch=firrtl2coq -- dune build && opam exec --switch=firrtl2coq -- dune runtest)
python3 arithmetic/scripts/generate_firrtl2coq_models.py
python3 arithmetic/scripts/generate_firrtl2coq_models.py --check
# 除法器复用的旧模型若不存在，先恢复生成物。
python3 arithmetic/scripts/regenerate.py --backend rocq
python3 arithmetic/scripts/check_firrtl2coq_divider.py --compile-only
python3 arithmetic/scripts/check_firrtl2coq_multiplier.py --jobs 2 --compile-only
```

生成入口实际调用 `tool/firrtl2coq/src/ocaml/_build/default/bin/main.exe`，输入为
`arithmetic/artifacts/chisel3/firrtl/{Radix2Divider,ArrayMulDataModule8}.lo.fir`。
`--check` 再次调用该工具，在临时目录生成并逐字比较两个电路共六份输出；本轮已实际通过。
相同内容不会改写时间戳，不会仅因再次生成就使证明缓存失效。
上述命令编译最终 Lemma 文件及其全部依赖，结果记录 `coqc: passed`、`coqchk: skipped`。去掉 `--compile-only` 可额外运行独立 `coqchk`；乘法器的 `--force` 可要求全量重编译。本轮没有执行这两项额外检查。

两个电路的 SystemVerilog 另存于 `arithmetic/artifacts/chisel3/systemverilog/`，
由 `python3 arithmetic/scripts/generate_firrtl_systemverilog.py` 使用固定 Scala FIRRTL 1.6.0
从同一 Low FIRRTL 生成；`--check` 重生成逐字对比和两个顶层的 Verilator lint 均已通过。
这不构成 FIRRTL 到 SV 的形式等价证明，编译器仍在可信边界内。

具体环境要求见 [证明说明](../verification/firrtl2coq/README.md)。应同时核对输入 FIRRTL、生成模型、证明源码和工具源码的哈希；仅记录分支名不足以复现。结果文件在忽略的 `arithmetic/build/firrtl2coq-*-proof/result.json`，所选验证流程成功后才生成；应分别查看 `coqc` 和 `coqchk` 字段，不能将文件存在等同于独立检查通过。生成 manifest 中的 `proved: false` 仅说明生成步骤不负责证明，不是最终验证结果。

修改工具 Coq 源码后，仅运行 dune 可能继续使用旧提取代码。必须按上述顺序重新提取。最终检查还应查看 `Print Assumptions`；本次两个上游类型相等性公理应明确披露，不能声称完全无公理。

## 8. 下次优先改进的组织方式

1. 在指定开发分支基础上开始，工具修复、主项目工具引用、证明和探索归档各自界限清楚，避免完成后再迁移历史。
2. 在生成大规模证明前，先完成最小复位、两级寄存器、重复实例和边界算术测试。
3. 尽早锁定最终目标的采样时刻、合法输入域和执行成功前提，把语义讨论写进文档。
4. 先建立可复用的局部求值、端口和提交引理，再生成电路专属实例；尽量减少重复展开。
5. 给每个生成文件记录生成器和命令，避免手工修改与生成版本分叉。
6. 用最终依赖清单确定交付范围；实验文件归档，并区分“证明依赖”和“生成脚本输入”。
7. 保留一次完整构建、独立检查和哈希记录。后续只改路径或文档时核对依赖未变，不必机械重复耗时证明。
